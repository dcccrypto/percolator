# SLICE-DIFF: what the Aristotle upload is, against the real engine

Pinned engine commit: **`c38b6b1e948393613059d133337d16dcc09cbd16`** (`dcccrypto/percolator`; `src/v16.rs` blob `7d3edfe8…`, `src/wide_math.rs` blob `97c6b16d…`; both blobs are also unchanged at this branch's HEAD). The uploaded files are the 6 in `project/` (`diff -r` of the downloaded archive against `project/` shows no difference). Generated by `slice_diff.py` (run it to reproduce sections A and B).

**Short answer.** Two of the six files are the engine's own code, byte for byte. The three functions that carry the payout logic are **not**: they are a hand transcription over plain structs, with the engine's account views, byte decoding, several calls, and all post-checks removed. The Aristotle results are proofs about that transcription plus the copied helpers. They are not proofs of `close_resolved_account_not_atomic`, `create_resolved_payout_receipt_if_needed` or `claim_resolved_payout_topup_core_not_atomic` as they are in the engine.

## Per-function differences (what each transcribed function drops or changes)

Engine line numbers are at `c38b6b1e`. Full hunks are in section B below.

### `create_resolved_payout_receipt_if_needed` (engine 25203-25245) → `close_path::create_resolved_payout_receipt_if_needed`
- Types changed: `&mut self` (market header view) → `pool: &mut PoolV16`; `account: &mut PortfolioV16ViewMut` → `&mut ClaimantV16`. Reads `account.header.pnl.get()` → `account.pnl`; `account.header.resolved_payout_receipt.try_to_runtime()?`/`present` decode → plain fields.
- Dropped: `self.initialize_resolved_payout_ledger_if_needed()?` (engine 25177-25201, 25209). In the engine that call captures the snapshot on the first receipt (reads `residual()`, `junior_claim_bound()`, `pnl_pos_bound_tot_num`, slots). The slice assumes the snapshot is already captured with a ledger that satisfies `Inv`.
- Dropped error paths: `decode_bool(...)?`, `try_to_runtime()?` on the ledger (can return Err on a malformed byte encoding); `from_runtime` writes become plain assignments. `self.recompute_resolved_payout_rate()` is inlined as `pool.ledger = kernel_recompute_resolved_payout_rate(pool.ledger)?` (same call, minus the byte decode/encode).
- Unchanged logic: the bound arithmetic, the two checked operations, the halted-flag-and-`RecoveryRequired` branch, the receipt contents.

### tail of `close_resolved_account_not_atomic` (engine 26643-26704) → `close_path::close_resolved_payout_tail`
- Not the whole function: engine 26580-26642 (the `Resolved`-mode check, source-domain preparation, lapsed-backing expiry, B-chunk side effects, `sync_account_fee_to_slot`, principal loss settlement, bankruptcy settlement, leg detach, `ProgressOnly` exits, `resolved_positive_payout_ready`, source-claim realisation) is **not in the slice at all**. Only the tail after them is. The slice replaces "the engine reached the tail" by two things: precondition `Inv`, and an added guard `if account.pnl < 0 { return Err(NonProgress) }` that does not exist in the engine (the engine returns `Ok(ProgressOnly)` there).
- Return type: engine `V16Result<ResolvedCloseOutcomeV16>` (`Closed { payout }`) → `V16Result<u128>` (the payout).
- Dropped call: `self.clear_fully_diluted_resolved_receipt_if_terminal(account)?` (engine 26672; body 26140-26160). It reads the ledger, calls `resolved_payout_rate_is_terminal()`, `resolved_positive_payout_ready()` and `resolved_receipt_claimable_now`, and may replace the receipt with `ResolvedPayoutReceiptV16::EMPTY`. The slice's own note says it only touches a receipt whose claimable is 0, which is true of the code, but the slice's results never see the receipt after that step, and `Inv`'s `receipts`/`paidLe` are stated over present receipts, so the engine's post-state can differ from the slice's (receipt EMPTY vs present-and-fully-paid).
- Dropped writes: `set_account_pnl(account, 0)` (engine 15218, updates positive-pnl aggregates and can return Err) → `account.pnl = 0`; `reserved_pnl = 0`, `fee_credits = 0`, `health_cert.valid = 0`.
- Dropped error paths (can only turn `Ok` into `Err`): `TokenValueFlowProofV16::capital_and_resolved_payout_to_external_out(..)?.validate()?`, `self.validate_shape()?`, `account.validate_with_market(&self.as_view())?`, all `decode_bool`/`try_to_runtime`/`from_runtime` byte conversions, and the header `V16PodU128::new/get`.
- Unchanged logic: the payout formula `min(capital + claimable, vault)`, `capital_paid`, `resolved_paid`, the receipt payment, the `vault` and `c_tot` updates.

### `claim_resolved_payout_topup_core_not_atomic` (engine 26492-26525) → `close_path::claim_resolved_payout_topup_core`
- Types as above. `resolved_receipt_claimable_now(receipt)` (reads the ledger from the header) → direct call on `pool.ledger`.
- Dropped: `self.clear_fully_diluted_resolved_receipt_if_terminal(account)?` in the `claimable == 0` branch (engine 26501); the `TokenValueFlowProofV16 …validate()?` check (26516-26523); the header `V16PodU128` decode/encode.

### `close_all` (new)
Not in the engine. The engine closes one account per call and the caller picks the order; `close_all` loops over `order` calling the tail, and returns `InvalidLeg` for an out-of-range index.

## What this means for each Aristotle result

- RC1 (`Spec.rc1_spec`): about the copied byte-identical functions `kernel_recompute_resolved_payout_rate` and `resolved_receipt_claimable_against_ledger` only. This one is about the engine's own code, with `wide_mul_div_floor_u128` as a premise and the account fields as plain integers.
- RC2, RC4, RC5, RC6, RC7: about the transcription. They say nothing about the engine's early steps, the omitted `clear_fully_diluted` receipt clearing, `set_account_pnl`'s aggregate bookkeeping, or the engine's validation calls. Results are for calls that return `Ok`; the engine can additionally return `Err` from the dropped checks, which does not break a statement that is conditional on `Ok`, but also means nothing here shows those checks pass.
- **RC3 (no `Err`, no panic) does not transfer to the engine.** It is the property most affected: the engine's tail has extra `Err` exits (the dropped validations and decodes) the slice does not have.
- `Inv` itself (`paidLe`, `backed`, `mirror`, `cover`, `rate`, `live`) is a statement we wrote about plain fields. That the engine's state always satisfies it when the close runs is **not shown anywhere**; `initialize_resolved_payout_ledger_if_needed` (which establishes the ledger) and the two operations that move the rate after the snapshot (`refine_resolved_unreceipted_bound_not_atomic`, `kernel_credit_post_snapshot_residual`) are outside the slice.
- Assumed by Aristotle: the `wide_mul_div_floor_u128` contract (see the status in README/JOB.md).
